# Поиск локаций — два пути с анти-галлюцинационным гейтом

Оба пути приводятся к одному формату записи локации с полями `relation_kind`
(filming_location | narrative_location) и `evidence_source` для различения
происхождения. Код: `app/lib/location-search.mjs`,
`app/lib/location-discovery-schema.mjs`; роуты — [[api-layer]].

## Путь 1 — канонический ([[wikidata]])

nearby-режим (гео-SPARQL вокруг точки) или work-режим (поиск произведения →
валидация типа по графу P31/P279 → локации по P915/P840). Только этот путь
выдаёт scene_match_token для [[film-imagery]] (реальные Q-id + TMDB id).

## Путь 2 — исследовательский ([[openai]] web_search)

Включается ТОЛЬКО после work-поиска, если matched_work найден, а локаций < 3.
Модель ищет до 5 мест города; сервер жёстко пост-фильтрует:

- `sourceUrl` обязан канонически совпасть с реально консультированным
  web_search-источником (Map из `web_search_call` в response.output) —
  непроцитированное отбрасывается;
- вне радиуса города — отбрасывается; дубль (то же имя или <50 м) —
  отбрасывается;
- id синтетический `web-<slug>-<lat>-<lng>` — не Q-id, поэтому такие локации
  никогда не получат кадр фильма.

## Грабли

- canonicalUrl режет hash и хвостовой «/», но НЕ query — источник с другими
  query-параметрами не сматчится и локация пропадёт.
- Инцидент 21.07: `format:"uri"` в Zod-схеме → 502 (OpenAI Structured Outputs
  не поддерживает) — URL в схеме модели только строкой.
- Клиент дедуплицирует discover-результаты по имени места и координатам
  ±0.0005.
