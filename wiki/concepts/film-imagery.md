# Кадр из фильма для локации — vision-гейт с capability-токеном

Задача: показать в карточке локации кадр, снятый именно здесь, а не случайный
backdrop. Конвейер `/api/film-image` ([[api-layer]]), логика —
`app/lib/scene-image-match.mjs`, `scene-match-token.mjs`, `tmdb-images.mjs`.

## Конвейер

1. **HMAC-токен**: `/api/locations` подписывает тройку `v1:tmdbId:workId:locId`
   (HMAC-SHA256 → base64url 43 символа) ТОЛЬКО для kind=film с известным TMDB
   id — клиент не может заказать платный vision для произвольных пар.
2. In-memory rate limit 12 req/10 мин на IP.
3. SPARQL-перепроверка связи work–P915–location + совпадение P4947.
4. До **24 backdrop-кандидатов** из TMDB ([[external-services]]).
5. [[openai]] vision сравнивает референс-фото места (allowlist https-хостов)
   с кандидатами; принимается ТОЛЬКО `confidence='high'` — иначе честный
   плейсхолдер + ссылка на Bing Images.

## Кэширование

- Канонизация query string с 307-redirect → максимум CDN-хитов; параметр
  `v=2` — версия матчера (bump инвалидирует кэш).
- Успешный матч — 30 дней; честный no-match — сутки; ошибки — private,
  no-store (НИКОГДА не кэшируются как «нет совпадения»).

## Грабли

- Негативные исходы приходят как 200 + `image_url:null` + `reason` — смотреть
  на reason, не на статус.
- Секрет подписи фолбэкается на OPENAI_API_KEY — ротация ключа инвалидирует
  токены ([[openai]]).
- Сериалы и книги кадров не получают (токен только film) — резерв: стиллы
  эпизодов TMDB, см. [[personal-collections-matrix]].
- История: сначала место-фото дублировалось как «кадр» (вводило в
  заблуждение) → PR #24 разделил; потом матчер смотрел только 6 популярных
  backdrops и промахивался → расширен до 24 (фикс 22.07).
